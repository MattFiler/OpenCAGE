# RuntimeUtils for Alien: Isolation

A fork of [RyanJGray's DevTools](https://github.com/RyanJGray/AlienIsolation.DevTools) to provide runtime utility in OpenCAGE to improve workflows for modders working in Alien: Isolation.

## Features

- **Hot reload** - press a key (INSERT by default) to restart the current level.
- **Unlock Mouse** - the game leaves the mouse cursor free, so OpenCAGE can be used beside it (flying its viewport while the game camera follows over Live Link, say). Clicking the game window and pressing a key (F4 by default) gives the game the mouse to look around with; pressing it again frees the cursor. While the cursor is free and a level is played, the game is told to let the cursor go when it would pin it to the middle of its window, the cursor is shown over the window, the mouse's movement, buttons and wheel are kept from the game while its window has the focus (so the camera doesn't turn as the cursor crosses it), and the game's own moves of the cursor (it puts the cursor back when a menu opens) are skipped. Menus are left alone: the game frees the cursor for them itself. The overlay notes each press of the key, and the first time a level is played with the cursor free.
- **Cap FPS** - the game runs at most `CapFps` frames a second. The game's clock never moves on less than 1/360 of a second a frame, so above 360 frames a second (a near-empty level with V-Sync off, say) the whole game runs faster than real time; the game has no frame limiter of its own besides V-Sync. Each frame waits at its start, before the game reads the clock, until its turn comes round (on a high-resolution timer, spinning for the last moment), so the frames keep to the cap and the game runs at its proper speed.
- **Debug text** - makes the `DebugText` and `DebugTextStacking` script entities work. Retail builds of the game disable these entities and strip the code that draws them, so the ASI re-enables them in memory and draws their text itself: `text` followed by any linked or non-default inputs in brackets, positioned by `alignment`, styled by `size` and `colour`, hidden after `duration` seconds (or kept until `stop` when the duration is -1, live-updating its inputs). Stacking text is a block on the middle left, newest at the bottom, five entries deep. Everything clears on level change. `DebugPositionMarker` draws XYZ axes at its `world_pos` while started, and `DebugEnvironmentMarker` draws its `text` there in its `colour` and `size`.

- **Zone loading** - the game only streams in the zones around the player and whatever the camera's view ray lands on, so a free camera (the Debug Menu's cinematic camera, or a tool someone injects themselves) can fly into areas that never load. The ASI exports `OpenCAGE_SetForceZoneLoading(bool)` so other injected tools can ask for the camera's surroundings while their camera is active. Live Link's camera sync, cubemap captures, Possess Characters and the Debug Menu's cinematic camera ask too while they move the camera. While any of them asks, the game works out the zone the camera is over itself (as it does for its other views), instead of being handed the player's, so the zones around the camera stream in as they would around the player; the player's own zone stays in. The game only streams zones while it runs, not while it is paused (its pause menu, or the Debug Menu's pause), so move the camera with the game running. With `LoadAllZones` on, every zone of the level is registered as viewed each frame and streams in - on a big level (HAB_AIRPORT, for one) that can be more than the game has memory for, and zones then stop finishing loading. Each of these only turns its own request on and off (so the cinematic camera turning off leaves `LoadAllZones` on).

- **Possess Characters** (off by default) - take one of the level's characters (the alien, an android, a human) and move it yourself. A key (F6 by default) opens a menu over the game listing the characters it runs, the one nearest the middle of the view first and then the nearest: click one, or pick it with the arrow keys and Enter, to take it (the menu also lets go of it; the key again or Escape closes it, and while it is open the cursor is shown and the keyboard and mouse are kept from the game). W/A/S/D move the character relative to the camera, Shift faster and Ctrl slower, C crouches it or stands it up again, the mouse turns the camera, which sits behind it, and the mouse wheel brings the camera closer or takes it further away (1.5 to 10 m). Each character the game runs has a behaviour tree deciding what it does, over a layer that carries out its orders (go somewhere, turn, move in a direction, crouch or stand). While a character is possessed its behaviour tree is not run - its senses, memory and the rest still are - and once a frame, where the tree would have run, it is given the game's own order to move in a direction (the one its scripted "move towards" command and one of its debug behaviours give), so it moves with its own animations, speeds and navigation mesh; C gives it the game's crouch or stand order (as the scripted idle command does) and it moves again once that is done. Letting go of the keys cuts the order short so it stops; letting go of the character takes the order back and its behaviour tree runs again. Meanwhile the keyboard (bar Escape) and mouse are kept from the game, so the player stands still, and the zones around the camera stream in (see Zone loading). OpenCAGE's viewport camera, when it drives the game camera, wins over the camera behind the character. Live Link's `POSSESS` takes a character by name, gives it a stick in place of the keys, crouches it and opens the menu, and `POSSESS_GET` reads what came of it.
- **Debug Menu** (off by default) - a window over the game (F7 by default opens and closes it). A row of groups along the top (Overview, Characters, AI, World, Scripts, Sound, Rendering, Performance, Game, Cinematic) each has its own row of tabs: debug views, overlays drawn over the game, switches and tools for the level's characters and their AI, the world, the level's scripts, the sound, the renderer, performance and the game itself. Its switches, numbers and buttons have names OpenCAGE can use over Live Link. See [Debug Menu](#debug-menu) below.
- **Don't write saves** (in the Debug Menu, or `DontWriteSaves=1` on its own) - the game writes nothing to the player's saves, progression or settings while it is on, and carries on as if it had saved, so a modded level, a checkpoint jump or a cheat can be tried without touching a real campaign. See [Don't write saves](#dont-write-saves).
- **Cinematic camera** (in the Debug Menu) - a free camera with camera tracks, look settings, HUD hiding, tools for the characters in a shot and screenshots: the Debug Menu's Cinematic group, which takes the place of the separate Cinematic Tools injector OpenCAGE used to start beside the game. See [Cinematic group](#cinematic-group).
- **Script debugger** (Live Link and the Debug Menu) - breakpoints set on nodes of OpenCAGE's flowgraphs stop the level's scripts, and the game with them, when one of the node's methods is about to be called; they then go on call by call. See [Script debugger](#script-debugger).
- **Live Link** - OpenCAGE edits the scripting of the level the game is running, without a reload: entities added, removed, re-parameterised or moved in the editor change in the running game, and the entity inspector can call an entity's methods (`start`, `trigger`, ...) in it. The game camera can also follow OpenCAGE's 3D viewport camera, or the viewport the game camera, and the CAGEAnimation editor's Animation Mode can hold or play an animation in the game; OpenCAGE's flowgraphs can light up the links the game's scripts follow as they run, and (with the Debug Menu on) stop them at breakpoints. It serves a WebSocket on `127.0.0.1:8765` (local connections only) that OpenCAGE connects to (launch the game from OpenCAGE with Live Link ticked in Launch Game's Debug tools; OpenCAGE connects by itself, and its Live Link button next to Launch Game turns it off and on). See [Live Link](#live-link) below.

## Configuration

Settings are read from `OpenCAGE.RuntimeUtils.ini` next to `AI.exe`. The file is optional; every key falls back to its default.

```ini
[RuntimeUtils]
HotReload=1          ; 1/0 - reload the current level on a key press
HotReloadKey=INSERT  ; a key name (INSERT, DELETE, HOME, END, PAGEUP, PAGEDOWN, F1..F12, A..Z, 0..9)
                     ; or a Windows virtual-key code, decimal or hex (e.g. 0x2D)
UnlockMouse=0               ; 1/0 - the game leaves the cursor free until the key below is pressed in its window
UnlockMouseKey=F4           ; the key that hands the mouse to the game and frees it again (named as HotReloadKey)
CapFps=0                    ; the most frames a second the game runs at (30, 60, 90, 120...); 0 = no cap
DebugText=1                 ; 1/0 - DebugText entities draw their text on screen
DebugTextStacking=1         ; 1/0 - DebugTextStacking entities draw their text on screen
DebugEnvironmentMarker=1    ; 1/0 - DebugEnvironmentMarker entities draw their text at a world position
DebugPositionMarker=1       ; 1/0 - DebugPositionMarker entities draw axes at a world position
LoadAllZones=0              ; 1/0 - stream every zone of the level in, not only those around the player
LiveLink=1                  ; 1/0 - let OpenCAGE edit the running level's scripting and call entity methods
LiveLinkPort=8765           ; the local port OpenCAGE connects to
LiveLinkCamera=1            ; 1/0 - let OpenCAGE's viewport camera drive the game camera when it asks (camera sync)
Possess=0                   ; 1/0 - Possess Characters: the key below opens a menu to take a character and move it yourself
PossessKey=F6               ; the key that opens and closes that menu (named as HotReloadKey)
DebugMenu=0                 ; 1/0 - the Debug Menu: the key below opens a window of debug views over the game
DebugMenuKey=F7             ; the key that opens and closes it (named as HotReloadKey)
DontWriteSaves=0            ; 1/0 - the Debug Menu's Don't write saves, on from the start (with DebugMenu=0 its hooks are
                            ; attached on their own; OpenCAGE writes 1 when Debug Menu and Don't Write Saves are both
                            ; ticked in Launch Game)

; Read only with DebugMenu=1 (each belongs to one of the Debug Menu's views):
BlockAchievements=0         ; 1/0 - Game > Saves' Block awards and stat writes, on from the start
CinematicCameraKey=F8       ; the key that turns the Cinematic group's free camera on and off (named as HotReloadKey)
CinematicScreenshotKey=F9   ; the key that takes a Cinematic group screenshot (named as HotReloadKey)
ExtraShadowLights=0         ; 1/0 - up to 16 shadow-casting lights a frame (the game's capture mode) instead of 4
D3DDebugLayer=0             ; 1/0 - the game's graphics device made with the Direct3D 11 debug layer, its messages listed in
                            ; Rendering > Developer (needs Windows' optional "Graphics Tools"; the game runs much slower)
RadiosityWarning=0          ; 1/0 - Rendering > Radiosity's warning over the game while a level runs without radiosity data
UiMemoryOverlay=0           ; 1/0 - Performance > Memory's UI memory overlay (the game's own), on from the start
DebugGraph=0                ; 1/0 - DebugGraph script entities plot their inputs (Scripts > Entities)
DebugMenuToggle=0           ; 1/0 - DebugMenuToggle script entities set a Debug Menu switch by name
DebugObjectMarker=0         ; 1/0 - DebugObjectMarker script entities label their object
DebugCaptureScreenShot=0    ; 1/0 - DebugCaptureScreenShot script entities save a screenshot (not on the GOG release)
```

A key named for the free camera or the screenshots that another helper which is on already uses (Hot Reload, Unlock Mouse, Possess or the Debug Menu), or a screenshot key the same as the free camera's, is left unset, and the log says so; so are any of the keys the free camera uses while it flies (F1 to F3, Home, Delete, End, Page Up and Page Down) that another helper uses.

OpenCAGE's Launch Game writes this file at every launch with the runtime utils installed. It rewrites the keys it has options for (`HotReload`, `HotReloadKey`, `UnlockMouse`, `UnlockMouseKey`, `CapFps`, the four `Debug...` entity keys, `LiveLink`, `Possess`, `PossessKey`, `DebugMenu`, `DebugMenuKey` and `DontWriteSaves`), drops `LiveLinkPort` (OpenCAGE only connects on 8765) and an older OpenCAGE's `CinematicTools`, and keeps every other key of the `[RuntimeUtils]` section that was set by hand (`LoadAllZones`, `LiveLinkCamera`, the cinematic keys, `D3DDebugLayer`...). Comments and other sections are not kept.

`OpenCAGE.RuntimeUtils.log` is written next to `AI.exe` each run: what Live Link did, every `DebugText` / `DebugTextStacking` that started, with its text, and what the Debug Menu's views attached (or why one could not).

## Debug Menu

`DebugMenu=1` (Launch Game's Debug Menu option) turns it on; its key (`DebugMenuKey`, F7 by default) opens and closes the window, and Escape closes it. Along the top is a row of groups, in amber, and under the group in front its own row of tabs; a group of one tab (Overview, Sound) shows that tab straight away. Each view lives in its own file and adds itself from a static initializer (`DEBUG_MENU.h`): its tab with `DEBUG_MENU::AddTab("Tab", order, draw, "Group")` (the same tab name again in the same group adds a section to that tab - the Player tab has six), anything it draws over the game with `AddOverlay`, and any hooks it needs with `AddHooks` (attached with the rest when `DebugMenu=1`, and taken out as the game closes). Overlays keep drawing once the window is closed, so the game can be played with them on. Notes along the top of the screen (a save kept back, the scripts held by the debugger, a new script error when asked for) stack under one another.

While the window is open the cursor is held free of the game window and shown, and the keyboard and mouse are the window's, kept from the game so the player stands still (key releases still reach it, so no key stays down). The characters are read once a frame as the frame is presented - after the game has finished updating them and before it starts on the next frame - with every read of the game guarded; work that has to change the game runs on the game's own threads (the entity thread between frames of the level's scripts, or the AI thread before the characters' behaviour is updated), queued from the window or from a command. Most tabs need a level running.

### Groups and tabs

Each group's switches, values and commands have the names in brackets as their prefix.

**Overview** (`info.`)
- *Info* - lines drawn in the top left corner of the game (beside the window while it is open), each a switch: the level, the zone the camera is in (by its Zone entity's name, which the game keeps) and how many zones are loaded, or all of them by name, the player's position, facing, speed, health, stance and light level, the camera, the frame rate, the game clock and its speed, the nearest alien, the characters, and from the Performance group the draw calls, the GPU frame time and the memory.

**Characters** (`characters.`, `player.`, `alien.`, `anim.`, `ai.`, `tools.invisible`, `tools.infinite_ammo`)
- *Characters* - the level's characters in a table; the selected one in detail (its entity and composite instance ids, state, target, sense meters, view cones, hearing, path), with labels, view cones, hearing ranges, paths and last known positions drawn over the game.
- *State* - the selected character's orders (from a script and from its own tasks), what its body is doing, the actions it is in, and its 105 state flags. Read only.
- *Control* - changes the selected NPC through the game's own calls: its motivations (force idle among them), a forced mood, its health (set, damage, set on fire, kill), and despawning it and spawning it again.
- *Animation* - the selected character's rigs, layers, animation trees and clips, root motion and IK, its skeleton drawn over the game; switches that turn off IK, velocity and turning warping, level of detail, one layer or the ragdoll pose; and the level's environment animations (doors, lifts, machinery) with their skeletons.
- *Player* - cheats (god mode, untargetable, invisible to the AI, the alien can't grab the player, infinite sprint, ammo and items, heal, set health, kill), teleport, the stealth light meter, hiding, what is under the player's feet (collision row, zone, sound and physical material) and the objectives, with the objective popup on demand.
- *Inventory* - the weapon in hand and the inventory, slot by slot, and giving the player things: items by name, every weapon, ammo, blueprints, keycards and the gating tools at a level; infinite items and torch batteries. All of it goes into the next save.
- *Input* - what the game thinks is pressed (the player's, the menus' or the game's debug input), also as an overlay to play with.
- *Alien* - its menace gauge, ambush and kill trap decisions, sweep area and vent targets; what it has learnt (each trick can be given or taken away - the game keeps this in memory only, never in a save), its setup and the director's numbers for it, and drawing it to a point.

**AI** (`bt.`, `tree_switch.`, `ai.`)
- *Behaviour Tree* - the selected character's tree: the path to the action it is carrying out, each node with its status, the branches and actions that started and ended, its debug texts; labels over the characters.
- *Squads* - the game's group of NPCs (objectives, targets, melee and pursuit permissions, awareness of the player) and the squads it makes of them, drawable over the game with the level's safe points.
- *Tree Switches* - the trees' debug switches (18 in the shipped trees, any a mod adds too) as tick boxes, for every character or only the selected one.
- *Tree Log* - every `DebugString` and `Assert` the trees reach, with the character, tree file, node number and count.
- *State Log* - the state changes the characters' body state machines log (moving, cover, dying, the weapon, shooting), and breadcrumbs: a trail of where characters went with a labelled crumb wherever something changed.
- *Tuning* - five tuning numbers the game reads every time it uses them (human and android melee range, android melee spot and grapple timings, the player's throw speed, explosion damage to allies). They last until the game is closed.

**World** (`inspect.`, `zones.`, `world.`, `nav.`, `physics.`)
- *Inspect* - a ray from the camera through the game's own queue of rays: the row of the level's collision map hit (its entity, composite instance and path, zone, layer, materials) and the model drawn there, which can glow or be boxed. OpenCAGE's Select Entity Under Game Crosshair uses it (`inspect.pick`).
- *Zones* - every zone as the streaming keeps it (state, priority, which views see it, links, what is still loading), the streaming as a whole, and why the camera is in its zone (the collision row its zone ray hit).
- *Overlays* - trigger and use-trigger boxes (flashing as they fire), splines, doors with the zone links they open, the pickup handling's interaction points, and measuring rings.
- *Navigation* - the nav mesh the level loaded (or that it has none), drawn by markup, class, height, barrier, traffic or flood; off-mesh connections, door barriers checked against the sound network, the AI's path searches, traversals and a path test.
- *Cover & Jobs* - cover segments and slots and who has them, the baked spotting, crawl-space and assault positions, and every AI job with its tasks.
- *Physics* - static collision checked against the collision map, physics bodies, character capsules, physics systems (PHYSICS.MAP), collision layers, the rays the game casts, and collision turned on and off by scripts.

**Scripts** (`debugger.`, `scripts.`)
- *Debugger* - whether the scripts are held and where, with Continue, Step, Step frame and Pause scripts, and every breakpoint (see [Script debugger](#script-debugger)).
- *Errors* - the game's own checks of script entities (173 report calls the shipped game leaves doing nothing, pointed at a list), and method calls the game dropped because their chain's entity was shut down.
- *Triggers* - the delayed calls waiting to run, and (switched on) how many calls each entity's methods run, to find trigger storms.
- *Progression* - the saved (persistent) script variables, the objectives and the campaign's progression. Read only.
- *Events* - global events and positions as they are sent, and who listens for them.
- *CAGEAnimations* - the level's CAGEAnimation entities, playing ones first, with time, length and whether they play a cutscene.
- *Entities* - `DebugGraph`, `DebugMenuToggle`, `DebugObjectMarker` and `DebugCaptureScreenShot` made to work again, each off unless switched on here or in the ini.
- *Profiler* - where the scripts spend the game's time, by entity, type or composite, in milliseconds per second of play.
- *Cameras* - the camera stack, behaviours, transitions, depth of field focus, camera animations and paths, drawable over the game.

**Sound** (`sound.`)
- *Sound* - the listener's room, what is playing, the event log, speech and dialogue, what the AI hears, the sound network and its doorways, states and music, sound banks; and tools: the listener held still or at the player, a noise made for the AI, any sound event played by name, the squads' dialogue.

**Rendering** (`render.`, `light.`)
- *Rendering* - 69 of the game's own switches for the renderer and the bounce light (radiosity).
- *Debug Views* - the game's own 15 full-screen debug views of the bounce light and the G-buffer (irradiance, albedo, normals, shininess, ambient occlusion...).
- *Lights* - the real-time lights drawn this frame (or every light of the level), the shadow budget, an overlay; a light muted or played alone, whole kinds left out.
- *Radiosity* - whether the level's bounce-light data loaded, the slices in its four slots and their streaming, the objects lit from its cube maps; a warning while a level runs without it.
- *Post* - the post-processing and fog as the game has them this frame, with the engine's switches to leave an effect out, hold or scale the exposure, or pick the tone mapping.
- *Targets* - the renderer's targets and textures as pictures (G-buffer, depth, shadow maps, lightmaps...).
- *Visibility* - why an object (by its mover index) is or isn't drawn, the zones the renderer treats as visible, a level-of-detail distance override, and the reflection maps.
- *Developer* - the Direct3D debug layer's messages (`D3DDebugLayer=1`) and shader hot reload (experimental).

**Performance** (`perf.`)
- *Frame* - frame rate and frame time with a graph (also over the game), the renderer's counts, and how full each of its fixed limits and pools is (lights, shadows, particles, views, GPU resources).
- *Timing* - CPU time per task of the game's frame and GPU time per render stage, each off until switched on.
- *Memory* - the game's memory heaps, the memory each kind of script entity takes, the process's memory and address space, the graphics card's memory. Its checkbox *The game's UI memory overlay* (`perf.ui_memory_overlay`, live; `UiMemoryOverlay=1` from the start) turns on the game's own overlay of the memory its UI takes, in MB on the right of the screen: yellow from 29.5 MB, red from 30.5 MB with a line saying the UI is out of its memory budget. It replaces Launch Game's old Enable UI Memory Overlay, which patched AI.exe on disk (an AI.exe still patched that way starts with it ticked).
- *Streaming* - the texture and model streaming heaps, what is waiting, and the textures drawn at low resolution right now.

**Game** (`game.`, `tools.`)
- *Game flow* - the game's flow state, the checkpoint in memory, the difficulty (changed live), and every level the game knows with a Load button.
- *Saves* - [Don't write saves](#dont-write-saves), what was kept back and the game's saving state; the achievements, with Block awards and stat writes.
- *Tools* - debug checkpoints and the level's own checkpoints with Jump buttons, Reload last checkpoint; Pause, Step and the game speed; the free camera; the alien's and the selected character's actions and logic flags.

**Cinematic** (`cinematic.`)
- *Free Camera*, *Tracks*, *Visuals*, *HUD*, *Cast*, *Screenshots* - see [Cinematic group](#cinematic-group).

### Named switches, values and commands

Each view names what OpenCAGE (or a test) can drive from outside the window, from a static initializer or the first time it runs: a switch (`AddSwitch("characters.view_cones", &flag)`, on or off), a value (`AddValue("game.speed", &number, min, max)`, kept between its min and max when set from outside) and a command (`AddCommand("player.give", "help text", fn)`: a button's action, or a report). A command is called on Live Link's socket thread with the text OpenCAGE sent; it queues game work onto the game's threads, or waits a couple of seconds for an answer from one (with no level running, or the game paused, it says it timed out, and the work is still done when the game comes round to it). The command `help` lists every command with the text it takes; `menu.ping_threads` and `menu.characters` test the menu itself.

Live Link's `DEBUG_MENU_CONTROL` (refused while `DebugMenu=0`) takes an op: 0 report, 1 open the window, 2 close it, 3 bring a tab to the front (by its name, else the first tab whose name holds it, else the first group whose name does, ignoring case), 4 select a character (the first whose name holds the text, else whose class does - the game names its alien "Alen"), 5 set a switch, 6 run a command with a line of text, 7 set a value. A command answers with what it says (and fails when it fails); every other op answers with the report: `open`, `group`, `tab`, `selected`, `tabs`, `groups`, `commands` and `values` (`name:number`), then every switch as `name=0|1`, a line each. A command that changes something shows its name in Live Link's line on screen for a few seconds; reports (lists, a status or state) don't, so they can be polled. OpenCAGE's script debugger and Select Entity Under Game Crosshair use these commands, and its MCP server's `runtime_utils` action `debug_menu` (`menu` report, open, close, tab, select, set, run or value) gives an AI assistant all of them.

### Don't write saves

Game > Saves' *Don't write saves* (`game.dont_write_saves`) keeps everything the game would write of the player's from the disk: checkpoint and mission saves (save stations included), the progression file (which also holds the game settings), the input settings and the graphics settings. The game carries on as if it had saved - a checkpoint still fires its "saved" outputs - and loading keeps working, from what was saved before. It works at four levels, each catching what the one above lets through:

- the game's own calls to save the progression and the settings return at once, as when the game's own "saves enabled" is off;
- the save system finishes any save or delete it is handed as a success at once, without its save thread ever writing it;
- the Steam Cloud's own writes, deletes and forgets (Steam and Epic Games Store releases), and a leaderboard's file upload, return at once;
- the game's own file calls refuse to create, change, delete or move a file in a save folder: My Games\Alien Isolation (GOG), The Creative Assembly\Alien Isolation (Epic Games Store) and the game's folder in the Steam user data.

The tab counts what was kept back and names the last one (with a note at the top of the screen for a few seconds, `game.save_notice`), and shows the game's saving state; `game.saves` reports the same, and `game.saves_check` checks the file guard with a path in the temporary folder that can't exist (nothing is written). The same tab's *Block awards and stat writes* (`game.block_achievements`, `BlockAchievements=1`) keeps the game from awarding achievements or changing achievement stats on the player's profile. Turn Don't write saves on before giving items, using the Player tab's cheats or jumping checkpoints on a real campaign: what they change can go into the next save.

`DontWriteSaves=1` turns it on from the start, before the game first saves. With `DebugMenu=1` it is the tab's switch, which can be turned off in game. With `DebugMenu=0` its hooks are attached on their own: saves are kept back for the whole run, with no window to turn it off and no note on screen (the log says "Don't write saves: on" with how many of its hooks attached). Launch Game writes `DontWriteSaves=1` only when Debug Menu and Don't Write Saves are both ticked, and rewrites it at every launch, so the menu-less way is for an ini set by hand for a game started some other way.

### Cinematic group

The Cinematic group is a free camera for shots and video, with the tools Cinematic Tools offered around it, so Launch Game's "Enable Cinematic Tools" and the separate injector it started beside the game are gone (OpenCAGE no longer ships the injector, and closes one an older OpenCAGE left waiting). The camera's flying and the track player follow Cinematic Tools, by Hattiwatti.

- **Free Camera** - its key (`CinematicCameraKey`, F8 by default) turns it on and off with the window open or closed, as do the tab's checkbox and Game > Tools' Free camera (`cinematic.camera`). It starts where the game camera is, looking the same way with the same field of view (after that, where it was left in the same level, unless "Start from the game camera" is ticked); the player is frozen and the game's keyboard, mouse and gamepad are kept from it (bar Escape, for the pause menu), and the zones around the camera stream in. Untick "Keep the game's input" to play on while the camera holds where it is.
  - Keys: W/A/S/D fly, Space and Ctrl go up and down, Shift is four times faster, Page Up/Down change the speed; the mouse or the arrow keys turn it, Q and E roll it, the mouse wheel or the numeric pad's + and - change the field of view; the numeric pad's 6/5, 8/9 and 3/2 change the depth of field's focus distance, focal length and f-number; F1 adds a track node, F2 deletes the last, F3 plays or stops the track; Home hides the HUD; Delete pauses the game and End steps it one frame while paused (`cinematic.keys` lists them).
  - A gamepad flies it too: the left stick moves, the triggers go up and down, the right stick turns, the shoulder buttons roll, the stick clicks change the field of view, the d-pad's up and down change the turn speed and B and Y the move speed.
  - The tab sets the speeds, field of view, roll and mouse sensitivity, locks the camera to the selected character or puts it behind one, moves the player to the camera, and saves and loads these settings as named profiles in `OpenCAGE.CinematicProfiles.ini`, next to `OpenCAGE.RuntimeUtils.ini`. Its Time section is the Game group's pause, step and game speed; nothing streams in while the game is paused, so fly to the shot first.
  - It takes the game camera from Live Link's camera sync while it flies (see Camera sync), gives way to a cubemap capture, does not turn on while a character is possessed (and turns off when one is), and turns off when the level changes. With Unlock Mouse on, the mouse only turns it once Unlock Mouse's key has given the game the mouse.
- **Tracks** - a track is a list of nodes, each a pose of the camera at a time; played, the camera moves through them on a smooth path (a Catmull-Rom spline through the nodes, its pace eased to keep to their times), in real time at the playback speed, once or looping, turning, zooming and focusing with the nodes as the track's locks say ("Play manually" moves along it with up and down instead). Nodes are added where the camera is, deleted, updated, gone to and moved in time, and the timeline scrubs the camera along the track; several tracks can be kept, and "Show the track" draws it over the game. Tracks are saved to and loaded from `OpenCAGE.CinematicTracks.txt` in the game folder (or another `.txt` named there, no folders).
- **Visuals** - the depth of field (focal length, focus distance, f-number) and the rest of the post-processing - brightness, contrast, saturation and tint, the frame's scale and offset (Cinematic Tools' "brightness" and "gamma"), bloom, motion blur, film grain, vignette, lens distortion, sharpness, full-screen blur, chromatic aberration - and the tone mapping's points, strengths and luminance scale, each set in place of the level's (`cinematic.override.<setting>`, `cinematic.<setting>`). While an override is off its value follows the level's, shown beside it, so turning it on starts from the level's value; a value set while it is off (by name, a track or a profile) is kept for when it is turned on. "Back to the level's values" turns every override off and lets go of such values. With the game's depth of field off in its graphics settings, the depth of field shows nothing.
- **HUD** - "Hide the HUD" (`cinematic.hide_hud`) hides the in-game and weapon HUD (Home while flying); in a challenge map it also hides the challenge mode's objectives, score and timer, unless "Also hide the challenge mode's objectives" (`cinematic.hide_hud_challenge`) is unticked. Every layer of the game's interface (the motion tracker, subtitles, prompts...) can also be hidden by itself (`cinematic.ui.<layer>`); leave the pause menu's layer alone.
- **Cast** - "Freeze NPCs" (`cinematic.freeze_npcs`) holds every character but the player idle where it stands, newly spawned ones too: people through the force idle motivation (their behaviour trees' idle branch then runs ahead of everything else, scripted orders included), the alien and the androids through their trees' debug switches (AI > Tree Switches: "Disable All Aliens", "Force Android Idle"). Their senses keep running and they still react to being hurt; an android following a script's orders carries on with them, and facehuggers have nothing to idle them. Turned off, only what it turned on is turned off again. The game keeps force idle in its saves, so a checkpoint saved while people are held brings them back idle. The tab also makes the player invisible to the AI, puts the camera behind a character or locks it to one, and moves the player to the camera. For a world that stops altogether, freeze time in the Free Camera tab.
- **Screenshots** - the frame as the game drew it, without the Debug Menu or anything else RuntimeUtils draws, saved as a `.bmp` in a `Screenshots` folder in the game folder, named after the level and the time; "Hide the HUD for the shot" (`cinematic.screenshot_hide_hud`) hides the HUD for the frames it takes. Its key is `CinematicScreenshotKey` (F9 by default), with the window open or closed (`cinematic.screenshot` takes one from OpenCAGE).

### Script debugger

OpenCAGE's flowgraphs set breakpoints on nodes (a node's menu, Set Breakpoint, or F9 over it; a method pin's menu for that one method), in the instance the composite was reached through from the level's root, or in every instance of it when it was opened from the composite browser. The level's scripts - and the game with them - stop when one of that entity's methods is about to be called, OpenCAGE brings the node to the front, and Continue (F8 there), Step (F10) or the Debug Menu's Scripts > Debugger tab let them go on. It needs Live Link and the Debug Menu: OpenCAGE drives it with `DEBUG_MENU_CONTROL`'s `debugger.` commands.

The game still has most of a script debugger of its own. Before each method call its scripts make, it looks the entity the call goes to (and the entity behind it, for a proxy) up in a list of breakpoints the shipped game leaves empty; when one is there it keeps the call back, ends the round of calls it was making, and calls a function with the breakpoint's number - a function the shipped game leaves empty, so nothing stops. Here that list is filled from the breakpoints set: an entry for each method in each running instance a breakpoint names, by the entity's id and the id of the composite instance it is in (as the game names entities in its own records), written under the game's own lock on its scripts on the entity thread - the frame after a change, after a level loads and every second (so instances spawned since are taken in) - and only while the level a breakpoint was set for runs. The game's call of the empty function is pointed at ours (its four distance bytes, checked first to reach that function in this build, and put back as the game closes), which notes what was hit - the held call, the entity it goes to, the composite instance holding it and the calls that led to it - and pauses the game with its own pause state's breakpoint reason, which stops the level's scripts and the game's clock as its pause menu does, at once rather than from the next frame. Continue takes that reason away: the game makes the held call without looking it up again, and carries on. Step lets the held call and the rest of the calls due at the same moment run (one round), then holds again; Step frame lets one whole frame of the game run. A level that unloads, or is loaded again, while held is let go. While the scripts are held a line along the top of the screen says so, and Live Link holds edits and method calls (see below), taking them as soon as the scripts go on. Where the call can't be found, the tab says "Script breakpoints are not available on this game release".

OpenCAGE polls the Debug Menu's report a few times a second while it has breakpoints or the scripts are held (the values `debugger.held`, `debugger.hit` and `debugger.version`; a report puts nothing on screen), reads `debugger.state` when the hit count moves and `debugger.list` when the list changes. When its Live Link goes off or OpenCAGE closes, it switches `debugger.breakpoints` off and lets held scripts go (the breakpoints are kept, and armed again when it connects); if OpenCAGE goes without doing so, Continue in Scripts > Debugger lets them go. Its Show Live States Above Nodes draws above the flowgraph's nodes what `debugger.entities` gives (the state flags - started, enabled, locked, opened... - of one running instance's entities, read under the game's lock on its scripts) and `debugger.values` (what entities read for their parameters now, each read on the entity thread with the game's own reader of that kind of value, following the parameter's links as the entity itself would). The other commands: `debugger.add_breakpoint` (a composite, an instance path or `*` for every instance - or a composite instance id - an entity and methods), `debugger.remove_breakpoint`, `debugger.clear`, `debugger.enable_breakpoint`, `debugger.list` (also `debugger.list_breakpoints`), `debugger.state`, `debugger.continue`, `debugger.step` (`cycle` or `frame`) and `debugger.pause`; the switch `debugger.breakpoints` off keeps the breakpoints but none stops the scripts.

### How some tabs work

**Behaviour trees** (AI > Behaviour Tree, Tree Switches and Tree Log) - the shipped game keeps no names for what the characters' behaviour trees are doing. As a level opens, the loading of its trees is followed: every node the game makes is noted with the tree file it came from, its number in that file (counted in document order, as OpenCAGE's behaviour tree editor has the file's nodes, the root being 0), its editor class, its Name and the attributes that say most about it (a branch's type, a debug switch's label and default, a debug text). After each run of a character's tree its state is copied: the path from the root to the action it is carrying out (the leading node), each node with its status (running, succeeded, failed, shutting down) and, for a condition, which way it went; the path to a better branch waiting for that action to shut down; its outer branch and the one before; and the branches active. **Behaviour Tree** shows all that for the character picked, with the tree it runs, the branches that started and ended and the leading actions that succeeded or failed (with their ages), and that character's debug texts; hovering a node gives its file and number and its other attributes. Ticking Show over characters labels the nearest dozen characters with their leading node and outer branch, and their latest debug text for a few seconds, coloured by status. The editor's `DebugString` and `Assert` actions do nothing in the shipped game but succeed; here each records its text against the character and node (the same text from the same pair within a second of its last is counted on its line rather than added as a new one), and **Tree Log** lists every one with the character, tree file, node number, count and age (the shipped trees use no `DebugString`, and their five asserts fire only in rare cases), also written to the log file. **Tree Switches** lets you flick the trees' debug switches, the `DebugMenuLinkTest` and `DebugMenuLinkItem` nodes, which only give their default in the game: each label found in the level's trees (18 in the shipped ones, any a mod adds too) gets a tick box, for every character or only the one picked; a ticked switch makes its tests go the other way from their default, and an item of the same label sets it back to its default when the tree reaches it (so a one-shot switch such as `Force_Breakout` unticks itself once acted on). They go back to unticked when a level loads. The direct control and gamepad control switches also need the game's own free camera (not the Debug Menu's), which the game never turns on, so they do nothing on their own. If the level's trees loaded before the menu could follow them, nodes show their editor class only (the class each node object has), and the switches are not available. Their names: `bt.overlay` (the labels over the characters), `bt.switches_selected_only`, and `tree_switch.` followed by a label exactly.

**Characters, Player and Alien** (Characters group) - three of the group's tabs show what the level's characters know and are doing, read from the game once a frame as it is presented. **Characters** lists them (name, class, distance from the camera, health, how aware of the player each is - or, for the alien, how full its menace gauge is - how alert and aggressive, its mood and the branch of its behaviour tree it is in); clicking one selects it and shows it in detail: who it is (with its entity's id and the id of the composite instance it is in, as OpenCAGE matches characters to their entities), its state and target, its eight sense meters (sight, weapon sounds, movement sounds, damage, touch, the flamethrower, seeing the torch, and all of them together) as bars with a tick at each of their four thresholds, coloured by the threshold reached, how long ago each sense last placed its enemy at each threshold and where, its flags and running timers, its view cones (from the game's own tables, with where its head is and looks), how far it hears, and its path (where it is going, how the pathfinding went, the nodes passed and ahead, and the corridor it steers through). Switches draw over the game, for the selected character or for every one: a label over the head (name, class, branch, awareness, alertness and aggression, a suspicion bar - the combined meter against its thresholds - and the target), the view cones (a flat sector from the head for each cone, as long as the cone and as wide as its width, in its own colour, with lines for its height, filled in when the player is in it by the game's own test), the hearing range, the path (passed nodes grey, the way to the current node white, the rest blue, the destination crossed) with its corridor, and the last known positions with their ages. **Player** shows the stealth light meter (the level - dark, partially lit or fully lit - against its two thresholds, the light found at each of its three sample points, their brightness and that through the AI's light curve), the other stealth factors, whether the player is hiding, and how close anyone is to spotting them (the most any NPC's combined meter is of its activated threshold, as the game works it out - the alien is shown on its own, as the game leaves it out); and the game's own screen tint for the light meter, which the game always asks to be off: that one ask is pointed at the tab's switch while the Debug Menu is on (put back when the runtime utils unload), with an opacity slider. **Alien** shows its menace gauge with its thresholds, whether it is menacing, paused or withdrawing, how many times it has menaced the player of how many its setup allows, its setup's name, its ambush and killtrap decision, the area it sweeps (drawn as the box the game works out for its stalking) and, in the vents, where it is heading and the best vents near it and the player. These views make only plain reads of the game, every one guarded, and the only game code they call is code that only reads (a sense's thresholds, how far a character hears, how many times the alien may menace, the area it sweeps); full detail is read for the selected character, and for those within 60 m of the camera when there are many. Each switch is a named one (`characters.labels`, `characters.view_cones`, `characters.hearing`, `characters.paths`, `characters.last_known`, each with `.all` for every character, `player.light_samples`, `player.light_tint`, `alien.sweep_area`, `alien.backstage_target`). The sections the Player and Alien tabs have besides (the cheats, teleport, the alien's learning and setup) do change the game, through its own calls on its own threads.

**Rendering switches** (Rendering > Rendering) - 69 of the game's own switches for the renderer and the bounce light (radiosity): passes left out (solid geometry, decals, deferred lighting, radiosity, transparency, lens flares, atmosphere, distortion, hair softening, skin scattering, morphs, the HUD...), FXAA and SMAA, what feeds the radiosity (static, dynamic and surface lights, door transfer, cube maps) and its debug switches (constant ambient, unlimited detail, no streaming...), shadows (cache, quality, shadow maps, filtering, culling, reflection maps), level of detail (one switch keeps every model at its most detailed), transparency (where it is drawn and how it is lit), exposure scaling, the histogram blur and light shafts, culling and sorting (occlusion culling, updating particles out of view, sorting by depth only), debug drawing (lens flares as quads, the surface effect overlay), the output views (the lit scene without tone mapping and grading, as linear, sRGB, gamma 2.0 or gamma 2.2 - only while their shader is loaded) and shader hot reload (experimental: the game reloads its shaders when a shader pack changes on disk). The shipped game asks each of these switches through a call to one of two shared functions, one always answering no and one always answering yes, so a switch is turned by rewriting the four distance bytes of its calls to reach the other answer: each call is first checked to be the expected call to the expected answer in this build (a switch that doesn't check out is greyed out), and is put back exactly as it was when the switch is turned back, on Reset all, and as the game closes. Some only do part of what their names suggest; each has a tooltip. Each switch is named `render.` and its name (`render.no_radiosity`, `render.disable_lods`...).

**Game > Tools** - lists the level's debug checkpoints (the active DebugCheckpoint script entities) with a Jump button each (handed to the entity manager on the entity thread, never while the game saves or another load is pending), then every checkpoint the level has activated, each with a Jump button that goes to it by its place in the list (so one with no name, or sharing a name with another, can be jumped to), and Reload last checkpoint, the game's own restart from the checkpoint in memory, as after a death. Most debug checkpoints start a part of a mission, which happens once per level load: jumping to a part that already ran leaves the screen black (load the level again first). Pause holds the whole game (its clock, the AI, physics, animation, zone streaming and the level's scripts) without the pause menu, Step lets one frame through (Step 10, ten), and Pause while this window is open holds the game while the window is open; the game speed goes from 0.05x to 4x through the game clock's own time scale (the one its slow-motion moments use - Cap FPS is unaffected). Free camera turns on the Cinematic group's free camera. The AI section acts on the alien or the selected character through the game's own functions on the AI thread: alert the alien to the player, withdraw it or cancel the withdrawal, force its menace aggressive or passive, reset an NPC or its senses and memory, and its logic flags (prevent all attacks, prevent grapples, block ambushes and kill traps, never aggressive, totally blind in the dark, lock backstage stalk, should break out and more) as checkboxes that follow the character's own. Invisible to the AI, infinite ammo and the other player cheats are in Characters > Player. The game also still serves Havok's Visual Debugger on `localhost:25001`, from which a Havok 2012.2 Visual Debugger client shows the physics world live. Names: `game.paused`, `game.step`, `game.speed`, `game.pause_while_open`, `game.list_checkpoints`, `game.jump_checkpoint`, `game.reload_checkpoint`, `game.list_debug_checkpoints`, `game.jump_debug_checkpoint`, `tools.free_camera`, `tools.flag.<flag>`...

**Animation** (Characters > Animation) - the tab shows what the selected character's animation system is doing, and switches drawing over the game for the selected character or every one: each character's posed skeleton (its bones from the final pose the game skins the mesh with, or any layer's own pose; left bones blue, right orange, dimmer when the character was not posed that frame; links close to the camera left out, so the player's own head does not fill the screen), bone names, bone axes, the helper bones the game works out each frame (head, hips, root, hands, feet), its velocity (what the animations give, what its movement asks for, and what they are warped to), its IK targets, and its heaviest tree and clip over its head. The tab has the character's rigs, animation and tree sets, stance, mood and equipment contexts and switches; the eight layers (used, level of detail, weight); every tree each layer runs, with its parameters and its nodes in a hierarchy (selectors with what they pick and why, blends with their values, leaves with the clip they play and where they are in it), optionally only those with weight; every clip playing (time against length, weight, speed, loops, ease, mirrored); root motion and velocity warping; the reference locator; and the IK solvers. The game keeps only name hashes here; their names come from the full name table in DATA\GLOBAL\ANIMATION.PAK, read once on a thread of its own the first time a name is wanted (until then, and for any it lacks, from the game's own shorter table). Its Switches section has animation switches, for every character or only the selected one (`anim.switches_selected_only`), each through one of the game's own steps in posing a character: IK off (`anim.no_ik`), velocity and turning warping off (`anim.no_linear_warping`, `anim.no_angular_warping`), level of detail off (every layer on at full weight, posed every frame; `anim.no_lod`), one layer off (`anim.layer_off.additive`, `.breathing`, `.look_at`, `.hand`, `.face`), the reference pose (`anim.reference_pose`) and the ragdoll's pose not copied onto the character (`anim.no_ragdoll_pose`); it also draws the reference locator while a matched animation lines a character up with it (`anim.reference_locator`) and shows how much each layer weighs on each group of bones. Environment animations lists the level's animated objects (what Play Environment Animation entities play) with their rig, clip, time and state, and draws their skeletons (`anim.env_skeletons`, `anim.env_labels`). The other switches: `anim.skeletons`, `anim.all`, `anim.bone_names`, `anim.bone_axes`, `anim.helper_bones`, `anim.velocity`, `anim.ik_targets`, `anim.labels`, `anim.only_contributing`.

**Sound** (Sound group) - for the game's sound, which the game itself draws nothing for. Hooks note every sound the game plays (with its event, the sound object it plays on and the script Sound entity behind it), each stimulus published for the AI (footsteps, gunfire, impacts) and each character working out how loud it heard one, each doorway's state as doors set it, the sound network's file as it loads (for its network names, which the game drops), every name the sound engine turns into an id, sound objects' names, subtitles and NPC dynamic dialogue; at each frame, while the tab or a drawing is on, the game's lock around the sound update is tried and the state copied. *Overview*: the listener, the network (room) it is in with its room type, reverb and ambience (and the blend the game gives it near a doorway), the alien's state and distance through the network, the threat and stealth levels, and the game's own occlusion and reverb debug switches. *Playing now*: what the sound engine is playing, with its owner, age, distance and room (one can be picked: how far it carries, and the doorways the game routes it through). *Event log*, *Speech and dialogue* (the speech queue and slots, the subtitle with its line of text and speaker, what the squads asked their characters to say), *What the AI hears* (each stimulus, who checked it and how loud they heard it, worked out again from the shortest route through the network's open doorways to show the same number, and a test route from the player to the selected character), *Sound network* (its networks and doorways, which doorways nothing has set since it loaded, and the door log), *States and music* and *Sound banks*. Its *Tools*: the listener held where it is or put at the player's head (the game moves the listener with the camera, so a free camera takes the hearing with it; `sound.listener_frozen`, `sound.listener_at_player`); a noise for the AI (gunfire made by the player, at the player or the crosshair point, with a loudness from 0 to 1, published as the game's own weapon notifiers publish it; `sound.noise_loudness`); any of the running level's sound events played by name at the camera, the player or the crosshair point, and stopped again (it plays only while its bank is loaded); and each squad's dynamic dialogue state. Drawn over the game: the network near the camera (nodes by network with each node's three shortest links, or every link with `sound.network_all_links`; doorways as squares named with their number and state, green open to red closed), what is playing where, the stimuli and who heard them, the selected route and what speaking characters say (`sound.network`, `sound.network_all_links`, `sound.playing`, `sound.stimuli`, `sound.route`, `sound.speech`).

## Live Link

The game keeps a level's `COMMANDS.PAK` in memory exactly as it is on disk (the entity manager reads the whole file into one block), and a composite template *is* the file's composite record, its arrays being offsets from the start of that block. So OpenCAGE sends a composite as a one-composite PAK image (written by CathodeLib), with the positions of the offset words in it; the ASI copies it into memory it never frees, rebases those offsets onto the block (32-bit wrap-around reaches anywhere), turns the parameters into the game's variable objects as the game does when it loads the file, and points the template at the new arrays. It then brings every running instance of the composite in line with the change, working out the difference against what the game is running:

- entities (and proxies) that went are reverted and shut down, taken out of their zones and removed from the instance;
- new ones are constructed as entities or proxies by the entity manager (which builds a whole instance for a composite), added, initialised and validated, and put in the instance's zones - as the game does when it creates and initialises an instance's entities;
- entities whose parameters changed - directly, or through an alias (an override of something inside a nested instance) - have their parameter cache flushed and are live edited (put back in their initial state, repositioned, and left to react to the edit themselves) through the game's own live edit;
- so are entities fed by a data link that was made, broken or re-pointed, as that changes the value they read just as editing the parameter would: the one the link is kept on when it reads its value through it, or the one at the other end when the link sends a value out into it. The image cannot say which links carry data, so OpenCAGE sends their pins with it; a link that fires a method needs nothing more than the flush below, and the composite's own variables are never live edited this way (that would start the whole instance over);
- every entity's cached parameters and links are flushed, so link changes are picked up.

Method calls are queued as triggers the way the game's own code queues them, so they run on the next frame like a link firing. Everything that touches entities runs on the entity thread, in a hook on the entity manager's per-frame processing. A composite that is not in the running level (a new one), and new models or other resources, need the level saved and loaded again.

Because a live edit puts an entity back in its initial state before the entity reacts to the edit, something that was started (a marker, a `Thinker`, a looping effect) stops when it is edited, unless it starts on reset: start it again.

Edits and method calls are held while the level's scripts are not running - the entity manager's script transport reads paused (1) from a level's load through its intro and opening cutscene (the game queues its own triggers then) and pause menu (2) while the game is paused, rather than running (5) - and carried out once they have run again for 5 s (a level start can let them run for a moment between its pauses); after 20 s of waiting they are turned away ("still starting" / "paused") and not carried out. They are held the same way while the Debug Menu's Pause (`game.paused`) or the script debugger holds the game, and taken as soon as it goes on, with no 5 s wait. OpenCAGE sends its own edits again by itself, and a method call from OpenCAGE waits for the edits made before it; anything else has to be sent again once `STATUS` says `playing=1`. Edits and calls for a level the game is not running are turned away at once. Each change of the transport is written to the log. Edits and calls pushed while a level was starting were found to be able to leave the game on a black loading screen for good. `STATUS` reports `playing` (edits are taken now), `loading`, and the game camera's position and facing.

**Camera sync.** With Live Link Camera (above OpenCAGE's 3D viewport) on "Sync viewport camera to game", OpenCAGE sends its viewport camera (`CAMERA`: position, forward, up and vertical field of view, in the game's world space) and the game renders from it. The ASI hooks the game's hand-over of the camera it picked to the renderer and the sound listener: it writes OpenCAGE's pose into that camera's state, lets the hand-over run, and puts the camera's own state back straight after - so the rendered frame (and what is heard) moves while the camera behaviours keep the game's camera. What the hand-over passes on stays OpenCAGE's until the next frame, though, so game logic that reads the rendered view follows the viewport too: camera viewcone triggers, the current camera FOV script value, the alien's checks for being in the player's view and camera-direction AI conditions. It works in gameplay, cutscenes, the pause menu and while a level starts: `CAMERA` is stored and answered at once, never held like edits. The pose applies while the OpenCAGE connection that sent it lasts and the level it was sent for is running - disconnecting gives the game its camera back; while no level or another level is running it waits, and applies again when its level is back - and a new pose is turned away for another level, when no level is running, or with `LiveLinkCamera=0` (OpenCAGE sends its latest pose again every 2 s while the sync is on, so the camera picks up once the level is there). The zones around the camera stream in while it applies (see Zone loading), as the game would otherwise only stream the zones around the player. The overlay shows "Camera: following OpenCAGE", the log each change, and `STATUS` `camera_sync=1`. While the Debug Menu's cinematic camera flies, it takes the camera from camera sync, which gets it back when the cinematic camera is turned off; meanwhile the overlay shows "Camera waiting: the Debug Menu's cinematic camera has it". A tool someone injects themselves that hooks the same hand-over (after this ASI does) still chains with it: while OpenCAGE drives the camera its pose wins, and the tool's camera shows again once OpenCAGE lets go.

On "Sync game camera to viewport" it goes the other way: OpenCAGE asks for the game's camera (`CAMERA_GET`) and puts its viewport camera there - position, facing and vertical field of view - taking no camera control of its own meanwhile. The same hook keeps the state of the camera it hands on every frame, before any pose of OpenCAGE's is written over it, so the answer is always the game's own camera as of its last frame (the Debug Menu's cinematic camera while it flies - so OpenCAGE following the game's camera follows it - or, while its camera is on, that of an injected tool that hooks the hand-over): position, unit forward and up, field of view and a frame counter. It is answered at once, and turned away when no level or another level is running, with `LiveLinkCamera=0`, and while no frame of the running level has been drawn from a camera in the last second (a level loading).

**Cubemap capture.** OpenCAGE's Capture (the Function button on an EnvironmentMap entity in its entity inspector, or File > Recapture All Cubemaps for every one in the level) asks the game for the six views of a cube from a point (`CAPTURE_CUBEMAP`: the point in world space, the face size, how many frames to hold each face, how long to wait for zones to stream in, and whether to leave the HUD or the lens effects on). While the capture runs it owns the game camera, ahead of camera sync and Possess: the camera hand-over hook renders from the point with a 90 degree vertical field of view looking along +X, -X, +Y, -Y, +Z and -Z of world space in turn, each with the up a cube face has, so each picture goes into a cube texture as it is. The zones around the point stream in (as for camera sync), and the first face waits until what is loaded has stayed the same for two seconds (a zone counts as loaded if it was seen loaded in the last 0.4 s, as a zone's loaded flag flickers with the camera away from the player), or until the wait runs out. Each face is held for its frames, then its picture is taken from the finished frame at the frame presentation, before the overlay is drawn on it: the middle square of the frame, as tall as the frame and so 90 degrees both ways, scaled down to the face size by averaging the pixels it covers in linear light. Meanwhile the game's flash interface (the HUD) is hidden through each piece's own hide flag, put back afterwards, and the post-processing settings' per-frame update is hooked to turn off film grain, vignette, chromatic aberration, lens distortion and depth of field; colour grading, bloom and tone mapping are left as the game has them. Key presses and the mouse are kept from the game too while its window has the focus (the game's keyboard is its key messages, and its mouse is raw input), so the player stands still if the game window is clicked into mid-capture - bar Escape, whose pause menu ends the capture - and the cursor is held free of the window as Unlock Mouse frees it, whether that is on or not. The answer comes when the capture ends, with the six faces as RGBA; it ends early, answered with why, if OpenCAGE disconnects, the level changes, the game is paused (nothing streams in then), or the game stops drawing. One capture runs at a time; the overlay says what it is waiting for and which face it is on.

**Live settings.** OpenCAGE's Radiosity, Hair and Skin Shading, and Global Constants editors change the running game as their numbers are edited (`SETTINGS`), rather than at the next level load. The game reads those settings files (radiosity, skin shading, hair shading, the glow round usable things, and the stealth and interaction constants) whenever a level opens, into numbers of its own that it hands the shaders, or the gameplay that uses them, afresh every frame - so each value is simply written where the game keeps it, and shows on the next frame. The radiosity's bounce values work inside its feedback, so the picture settles over a number of frames, and bounce values far above 1 can make it run away until the next level load. Keys the game reads but never uses (the radiosity file's last two, four in the hair file) are answered as such. A value lasts until the next level load, when the game reads the file again (which the editor has saved it to). `SETTINGS_GET` reads back what the game holds.

**Animation drive.** In Animation Mode, OpenCAGE's CAGEAnimation editor drives the animation in the running game (`ANIMATION`): it holds it at the playhead while that is scrubbed, plays it from a time (at a rate, looping or not, and running its event tracks or not), and gives it back afterwards. The request is stored and answered at once, never held like edits, and the entity thread carries it out every frame, straight after the queued requests and before the game's own processing - so a keyframe edit pushed in the same frame, which binds the animation afresh, is held at the playhead before the frame is drawn. It finds the animation by the instance path, as a method call does (or in every running instance of its composite), and applies the time with the game's own function that applies an animation at a time, so every track the level binds to it behaves as it does in the level. If the game is playing the animation, only the flag that has the game advance it every frame is cleared - it is not stopped, and nothing fires. A hold never runs the event tracks, and neither a hold nor play ever reaches the animation's length, where the game would finish it and fire its finished and interrupted outputs into the level. Giving it back puts back its own times and flags (as the level's logic left them, if a script started or stopped it while it was driven), applies its own time again and lets the game advance it again if it did before - unless the level's logic started or stopped it since the drive last looked at it, in which case it is left just as that left it. An animation the game showed nothing of when it was taken (not started, not advanced, at its start - one it never applied, say) also has the entities it moves put back as they were then, since its pose at its start is not what they showed (another animation may have moved them): an entity's transform is set back exactly (one the game could not give then is left where the animation's own time puts it), and a track's number is put back under what its entity shows, which reads it the next time it reads its parameters. Giving it back happens on a release, when another animation is asked for, and when OpenCAGE disconnects, while a level that goes takes the animation with it. Nothing is applied or given back while edits must wait (a level starting, the pause menu, a cutscene or a message on screen): `ANIMATION_GET` then says `state=waiting` and why. Disabled animations, cinematics (an animation that plays a cutscene clip) and animations whose zone is not loaded are not taken, and `ANIMATION_GET` says so; one already taken is driven on through up to a second of its zone not being loaded, counted over the frames that look at it (with the game camera away from the player, the zone's flag drops for a frame or two at a time - the game itself applies an animation whatever its zone when a script stops or refreshes it), and only then waits for it. The log has a line for each animation taken, taken again (the level's logic changed it) and given back, with its state flags and times; the overlay notes when OpenCAGE takes an animation and gives it back, and `STATUS` says `animation=1` while it has one taken (held, played, or waiting to be given back). `ANIMATION_GET`'s `sequence` is that of the last request a frame applied, so OpenCAGE can tell when its latest one shows.

**Script activity.** With Activity on in a composite's flowgraph, OpenCAGE lights up the links the running game's scripts follow. It tells the game which composite instances it shows (`TRACE`: a composite and the instance path to it from the level's root, or every instance of the composite, up to 512 at a time) and takes what the game noted several times a second (`TRACE_GET`). The ASI hooks four things in the game, only to read: the one function every relay goes through, which fires an output of an entity and follows each logic link out of it (a composite instance firing one of its own pins goes through it too, as does a proxy); the game's readers of each kind of parameter value - once a reader has read, the links its entity's parameter cache holds for that parameter, read under the game's own lock on the cache, are the data links the read followed (at most 64 for one pin - a pin with more is counted in the log); the game's lookup of the entities attached to a pin, which every write of an output through its data links goes through (and which goes on, step by step, through a composite instance's pins), its links read from the cache the same way (a link from an entity to its own composite's variable is not kept there, so a write through it is not seen); and the entity manager's queueing of each method call a fired output's logic link makes (a method OpenCAGE calls itself, with `CALL_METHOD`, is noted too, with no caller). Each activity is kept when either end sits in a watched instance, or is one: an entity firing an output, reading a parameter through a link, sending a value out through one (both with the entity and pin at the link's other end), or having a method called through one (with the entity that called and its output), told by its id, the composite holding it, the instance path to that and, for an instance, the composite it is an instance of. They are added up between takes - one record per distinct activity, with how many times it happened and how long ago it last did - and a take hands them all over and starts afresh; at most 4096 are kept between takes, and any more are counted as dropped. Records are binary (see `TRACE_GET` in `LIVE_LINK_SERVER.h`). While nothing is traced the hooks only check a flag; while tracing, the composites of an entity's owner (and of the entity, for an instance) are checked against the watched ones (a hash set, so the check takes no longer with more watches) before anything more is read, every read of the game's memory is guarded (a fault drops that one activity, and is logged once), and the hooks, which run on several of the game's threads, share their records behind a reader/writer lock. `TRACE` and `TRACE_GET` are answered at once, never held like edits; tracing is for the level it was asked for (another level running turns them away - and a `TRACE` turned away for that stops the trace that was running), and belongs to the connection that asked - a disconnect stops it. The log has a line when tracing starts, and when it stops or changes, with how many of the game's calls it looked at and the time it took them; `STATUS` says `trace=1` while this connection traces.

Messages are binary, little-endian: `u32 'OCLL'`, `u16` version (1), `u16` command, `u32` request id, then the command's data (see `LIVE_LINK_SERVER.h`). Each is answered with the same header (command | 0x8000), `u8` success, a `u32`-length message, and any data. Commands: `STATUS`, `CALL_METHOD`, `APPLY_COMPOSITE`, `LOAD_LEVEL`, `SCREENSHOT` (the back buffer to a .bmp), `DESCRIBE` (a composite's running instances), `CAMERA` (a pose for the game camera to render from, or to let go of it), `CAMERA_GET` (the game camera's own pose, as of its last frame), `ANIMATION` (hold or play a CAGEAnimation, or give it back), `ANIMATION_GET` (what the game did with it, as of its last frame), `TRACE` (which composite instances to note script activity in, or stop), `TRACE_GET` (the activity noted since the last take), `POSSESS` (take a character, give it a stick, or let go), `POSSESS_GET` (what is possessed, where it is, and the level's characters) `CAPTURE_CUBEMAP` (the six faces of a cube from a point), `SETTINGS` (change numbers from the game's settings files), `SETTINGS_GET` (what it holds for them now) and `DEBUG_MENU_CONTROL` (drive the Debug Menu: its window, tabs, selection, switches, values and commands - see [Named switches, values and commands](#named-switches-values-and-commands)). The older JSON text message `{"version":1,"load_level":"..."}` still loads a level.

## Building

Build `OpenCAGE.RuntimeUtils.vcxproj` as Release|Win32. When building from the command line pass the folder above this one (`Source`) as the solution directory, e.g. `msbuild OpenCAGE.RuntimeUtils.vcxproj /p:Configuration=Release /p:Platform=Win32 /p:SolutionDir=<path to Source>\`. The output is `Build/runtimeutils/OpenCAGE.RuntimeUtils.asi` at the top of the repository, loaded by the bundled `winmm.dll` ASI loader (which OpenCAGE copies into the game folder as `d3d11.dll`).

The runtime utils work with the Steam, GOG and Epic Games Store releases of `AI.exe`, and tell them apart by the build stamp and size in its header. The code names every game address by where the Steam build has it; `GameAddresses.h` gives the GOG and Epic Games Store builds' for each, and `DevTools.cpp` looks them up. The three are the same game code built for each store, so they share layouts and differ only in where things sit. A new game address needs a row in `GameAddresses.h` before the other two builds can use it. Any other `AI.exe` build gets a warning at start, and nothing is hooked. A Debug Menu feature whose address a release lacks is greyed out there, or says it is not available on that release: the Rendering tab's Update particles out of view on the Epic Games Store release, and the `DebugCaptureScreenShot` entity on GOG. GOG has no Steam Cloud, so Don't write saves has no Steam Cloud calls to stop there; its other three levels work the same.
